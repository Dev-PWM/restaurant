# MasaFlow real-time suite

## Scope and boundaries

The v0.3 suite serves three independent React/TypeScript/Tailwind applications. Express and Socket.io in `server.js` own the only live ledger. `shared/types/realtime.ts` defines the contracts imported by both TSX and the checked JavaScript server/engine. The previous HTML/SSE implementation is preserved as `legacy-server.cjs`, along with its historical tests and data tools; the new service neither serves it nor executes its hardware integrations.

The operational lifecycle is `review → cooking → ready → completed`; unpaid tickets may end as `no_show` from review or ready, but not while cooking. `draft` remains in the shared union for pre-submission use. A customer submits a ticket into review; staff acceptance starts cooking. Cash is recorded only when the ready order is handed over, and that payment completes the ticket. Status and payment changes are server-confirmed, never optimistic. Existing v3 `unpaid` tickets migrate to `review`; older `acceptedAt` values are inferred from their prior payment/creation timestamps.

## Cash contract

Every monetary field ends in `Cents` and uses safe integer MXN centavos. Menu prices are final prices; this suite does not add tax or convert legacy currencies. The server ignores client totals and prices the selected menu IDs, modifier IDs, and quantities. Each order freezes the resulting line items. Sold-out changes stop new submissions; existing accepted tickets retain their agreed price and remain payable.

New payments are recorded with a `method` of `cash` or `spei` (a missing method on an older receipt loads as cash). A cash payment accepts the order total and the tender received, and calculates change without a tip option. A SPEI transfer must be the exact total with no change, and it is money in the bank, not in the drawer. Shift totals therefore reconcile as `revenueCents = cashCents + speiCents`, where `cashCents = tenderedCents - changeCents`; `tenderedCents` and `changeCents` count cash only. The analytics screen shows sales, received cash and change, and splits sales into cash and SPEI only once a transfer exists (so an all-cash shift never repeats its own total); every ledger row is labeled by method. A retried payment must repeat the same amount and method; anything else is a `PAYMENT_CONFLICT`. Each order also carries the customer's `paymentIntent` (their choice at checkout, default cash), which is only a hint for the cashier: the transaction records what really happened. Historical v3 receipts that recorded tips retain their original receipt fields and cash reconciliation when loaded, but tips are not included in current metrics, displayed in the interface, or recorded on new payments. Revenue is recognized only at pickup payment, which atomically records the receipt and completes the order. A transaction can be inserted only once. Item volume and revenue rankings use completed (handed-off) orders. The ledger includes completed paid tickets plus unpaid no-shows after removal from the queue; no-shows have no transaction and contribute zero revenue. `voidCount` counts these unpaid cancellations only; it is not a count of refunded paid receipts. The UI labels these different populations explicitly.

## Owner-made dishes

`admin_add_menu_item` (staff-only) adds a dish. **The POS has no screen for it any more:** the «Crear Platillo» button and its form were removed on 2026-10-09, and the command and its tests stay on the server. A client sends a UUID with the request, and the server keys the dish `custom-<uuid>`: repeating the same request after a lost acknowledgement returns success without adding a second dish, and reusing the id with different content is an `ITEM_CONFLICT`. The name (1-60 characters), section (one of `CATEGORY_MODIFIERS` in `shared/realtime/catalog.js`), price (a positive whole number of centavos up to $10,000.00) and description (up to 140 characters) are validated, and a second dish with the same name in the same section is a `DUPLICATE_ITEM`. The dish's options are not chosen by the client: they come from the section, from the same table the printed menu uses, so a new huarache offers the $10 quesillo and the required comal/frito choice, and a drink offers nothing. The menu is broadcast to every open customer screen. A dish cannot be deleted from the app: switch it to «Agotado» in Inventario to take it off the menu.

## Tables and dine-in

The ledger holds `tables` (`{number, status, occupiedSince}`; `TABLE_COUNT` in `shared/realtime/catalog.js`, currently 3). Staff tap a table on the POS (`pos_set_table`, staff-only and idempotent: repeating a status changes nothing and does not bump the revision) to mark it occupied or free it. Every snapshot carries the tables, including the customer's: only a number, a status and a time, no names or amounts. Every snapshot also carries `queueNumbers`, the numbers (and only the numbers) of the orders still in review or cooking; a customer's snapshot holds just their own orders, so this is how their screen counts how many are ahead of them (`apps/client-web/src/pages/OrderStatus.tsx`). A server without the field is handled: the screen falls back to the customer's own orders. An order carries `orderType` (`takeout` by default, so older phones and older orders are unchanged). A `dine_in` order is refused with `NO_TABLES` only when it is a new order and every table is occupied; a retry of an order already accepted still succeeds. **A dine-in order never changes a table**: staff mark the table when they actually seat someone. Closing the shift frees every table. A ledger saved before tables existed loads with all tables free (no version bump), and one saved with fewer tables than `TABLE_COUNT` is topped up.

## Durable state and retries

`data.json` lives in `.masaflow-realtime/` by default. Every mutation clones the current state, validates invariants, writes and fsyncs a temporary file, renames it atomically, and fsyncs the containing directory before acknowledging success or broadcasting. A failure before replacement leaves memory unchanged. If directory flushing fails after replacement, memory follows the replaced live file and further mutations are blocked until restart and ledger verification; the operation is not acknowledged as successful. An uncertain archive flush blocks reset and also requires restart. A directory writer lock prevents two servers from owning the same data. Corrupt files fail startup rather than being silently replaced. Restart recalculates metrics from validated records.

The customer persists a session UUID, pending request, and active order ID in localStorage. A request ID is stable until a definitive response arrives. Retrying the same ID/payload returns the existing order; conflicting content is rejected. Old shift IDs prevent a timed-out submission from being recreated after a shift close. New orders are not automatically replayed on reconnect.

Closeout requires an empty queue and matching shift/revision. The complete state and final metrics are written to a dated, shift-unique `archive_*.json` before resetting. Stock state is preserved, order numbers reset, web orders resume. A persisted closed-shift receipt makes retries return the same archive without closing the new shift. An interrupted close can safely retry. Closed-shift receipts are small, but grow over time; order histories live in separate archives.

## Transport and security

Client events: `submit_client_order`, `pos_order_paid`, `pos_update_status`, `pos_mark_noshow`, `admin_toggle_stock`, `admin_add_menu_item`, `pos_toggle_accepting_orders`, `pos_set_table`, `pos_close_shift`, `request_init`, `staff_login`, `staff_logout`.

Server events: `init_data`, `state_updated`, `menu_updated`, `metrics_updated`, `staff_expired`. Event acknowledgements include `ok` and a typed error code. The provider listens once per app, requests init on every connection, retains last known data during an outage, and disables writes until a fresh snapshot is received. Ack timeouts require reconciliation and idempotent retry.

Staff credential verification is on the server. LAN mode requires an explicitly configured four-digit PIN; public HTTPS mode requires a unique 12–256 character password. Neither credential is sent in snapshots or bundled into the frontends. Successful login returns a random 12-hour token; every staff event verifies it. Restart invalidates tokens. Logout revokes the token across connected sockets. Failed sign-ins are rate-limited by client IP across socket reconnects. The loopback development proxy appends a forwarded address; public mode trusts the final address supplied by the isolated Caddy service. Successful sign-ins do not consume the failure limit. Initial snapshot requests are bounded per socket, and broadcasts reuse one immutable state copy for all peers. Customer snapshots contain only orders belonging to that customer's random session capability; global financial data goes only to authorized staff. Public health returns no ledger data. Public Socket.IO access requires the configured HTTPS origin; authorization is still mandatory.

A PIN is intended for a trusted restaurant LAN. The separate `compose.public.yaml` stack provides an HTTPS Caddy gateway and password mode for a public host; it does not purchase a domain or provision hosting. This project does not create tunnels, payment integrations, printer commands, or drawer kicks. LAN mode has local network diagnostics and QR codes; public mode disables those endpoints and mDNS announcements.

## UI and visualization design

The POS shows three stable lanes—review, cooking, and ready for pickup—with explicit counts. Review tickets pulse red after 3 minutes and cooking tickets after 15 minutes; reduced motion removes the pulse. Staff can void an order in review or mark a ready unpaid order No-Show; the complete ticket remains in history, while no-show revenue and sold-item metrics remain zero. Omissions use red plus explicit `Sin…` text; extras use green plus `Extra…` text. Native dialog elements provide modal focus behavior and Escape dismissal. All controls remain usable by keyboard and touch. Orders and cash records are digital; the runtime exposes no printer or drawer hardware commands.

Analytics uses one DOM bar list, a compact cash summary, and a semantic ledger. There is no Canvas/WebGL or chart dependency. Quantity is encoded by bar width against the current maximum and always printed as text, so no hover is necessary. Financial fields remain text, not rounded visual estimates. The ledger renders 50 rows per page, can filter by name/ticket/status, and exports CSV with formula-injection protection. Staff pages stack in portrait; only the wide ledger scrolls horizontally inside its container. Controls wrap above the main evidence. No live chart animation competes with the workflow.

Updates are event-driven full snapshots suitable for a single counter. Pending active tickets are capped at 500; request sizes and event rates are bounded. Long shifts increase snapshot size because the full current ledger is held in memory. Close shifts regularly; for multi-store or very high-volume use, replace full snapshots with versioned deltas and a transactional database. This implementation deliberately targets one restaurant and one authoritative writer.

## Verification

`npm run typecheck` checks all new frontends and the server's JSDoc imports. `npm test` runs both retained legacy regression coverage and `tests/realtime.test.js`, which exercises the new engine and real Socket.io connections. `npm run build` produces three independent Vite bundles. Browser acceptance covers the cash workflow, customer refresh recovery, PIN gate, live inventory, pause, no-show history, offline/reconnect behavior, responsive layout and shift close. Legacy tests are explicitly routed to `legacy-server.cjs`; they are not evidence that the v0.3 events work.

## Browser page translation

The owner reads the Spanish screens through Chrome Translate. A page translator replaces every text node React rendered with `<font><font>…</font></font>`, so React's next `insertBefore`/`removeChild` throws `NotFoundError` and, with nothing to catch it, the whole app unmounts (a white page until reload). `shared/ui/translation-guard.ts` is installed first in all three entry points: it remembers which wrapper replaced which text node and redirects React's removal, insertion and text updates to the wrapper, so translation keeps working. `shared/ui/AppCrashBoundary.tsx` is the safety net for any other crash: inside the realtime provider and PIN gate, so the socket and staff session survive, it rebuilds the screen at most twice per 30 seconds and then shows a button. Unmounting the POS board flushes any payment still in its undo window, so a crash cannot drop a cash payment. Do not switch translation off (`translate="no"`) to avoid this: people rely on it. Proper names such as ¡Izquierdo! carry `translate="no"` so they are not mistranslated. To test, replace each text node with the nested `<font>` wrapper (both `replaceChild` and insert-then-remove), repeat after every click, and check that labels still match their state.
